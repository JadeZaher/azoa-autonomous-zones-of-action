### Concrete EVM protocol

Pinned `ethereum/contracts/bridge/Bridge.sol` and its ABI are authoritative. Source stages use token metadata/origin inspection, bounded ERC-20 allowance when needed, `attestToken`, `transferTokens` or native-ETH wrapping transfer. Target uses wrapped-asset registration (`createWrapped`, or authenticated metadata update when explicitly requested) and `completeTransfer` / native unwrapping variant only when the caller selects that exact disposition. The ordinary baseline is WTT payload type 1; arbitrary payload type 3 application dispatch is not silently accepted as a fungible transfer.

Observation requires finalized receipt, exact destination bridge and selector/arguments, expected core `LogMessagePublished` event and emitter, payload bytes, nonce and sequence. Do not copy the upstream convenience parser's first-log selection: its own source labels that shortcut unsafe. Claim exactly one publication matching the frozen stage, including emitter and payload; unrelated/duplicate candidates fail attribution. Redemption proof includes on-chain completion by body digest, exact recipient/asset mapping and finalized transfer evidence.

### Concrete Solana protocol

Pinned SDK `solana/tokenBridge/coder/instruction.ts` and instruction/account files define Solitaire one-byte instruction discriminants and little-endian fields, not Anchor's usual eight-byte discriminator. AttestToken=1, CompleteNative=2, CompleteWrapped=3, TransferWrapped=4, TransferNative=5, CreateWrapped=7. Transfer body contains nonce u32, amount u64, fee u64, 32-byte destination and chain u16. Complete instructions take their transfer body from a validated posted VAA account.

Source native/wrapped transfer plans include exact SPL source account/mint/owner, bridge config, custody/authority signer PDAs, core bridge/message/emitter/sequence/fee-collector accounts, system/token programs and required sysvars. Permit only the precise required delegation to the bridge authority and bounded amount; native SOL wrapping/unwrapping uses a separately identified temporary token account with bound rent destination. No user account owner/rekey/close substitution is permitted.

Target stages include guardian-signature verification through the actual secp256k1/core instructions, signature-set account, PostVAA, CreateWrapped when origin metadata lacks registration, recipient ATA creation when absent, then CompleteNative or CompleteWrapped. PDA/account schemas come from the pinned account derivation files, including guardian set, posted VAA, claim, endpoint, wrapped mint/meta and custody. Account ownership/data and executable program identity must be checked. Signature verification and posted-VAA prerequisites may need multiple exact transactions; each is durable and recoverable.

Message and signature-set keys are not derived from a public operation hash or re-derived from a rotatable wallet secret. Under a current caller custody authorization, preparation generates one CSPRNG Ed25519 stage seed and atomically claims its **encrypted** key envelope under unique `(operation, stage-role, generation)`. The envelope records public key, actual encryption-key version, AES-GCM nonce/tag/ciphertext and associated-data identity (protocol/network, actor/tenant, wallet, operation, role, generation). Only the claim winner is used; losing candidates are zeroed. The protected key claim must commit before any stage signature. Lost preparation response and wallet key rotation load that same winning seed/public key, never allocate a replacement.

A dedicated versioned stage-key protector uses an explicit active key ID and retained decryption key versions; it does not silently label the existing unversioned WalletKeyService ciphertext as versioned. Encryption-key rotation rewraps envelopes by CAS while retaining prior decryption versions until no unresolved envelope depends on them. Startup/maintenance verifies all unresolved key versions remain retrievable; missing versions fail configuration readiness and require restoration, never a new stage seed. Operator key retirement is disallowed while references remain. Decryption and signing still require current scoped custody authority for fresh effects; an encrypted seed is not a reusable authorization token. Seed/private plaintext stays in zeroable buffers and is never returned/logged. The read-only quote models the exact signer count without key allocation; winning preparation binds the public key and canonical message. Program/config coordination includes this protector/keyring without changing global wallet-key rotation semantics.

Source attribution uses the exact finalized transaction and core invocation/message account owned by the configured core program, with full emitted body/sequence/nonce/payload verification. Bare `Program log: Sequence:` text is insufficient because another program may print it. Recovery checks historical message evidence and exact signed transaction, not merely today's sequence account.

### Concrete Algorand protocol

Pinned `algorand/token_bridge.py`, `wormhole_core.py`, `sdk/js/src/algorand/Algorand.ts` and token_bridge transfer/attest helpers define the group contract. Source uses core-emitter and native/origin storage logic-signature account prerequisites, message fee payment, asset opt-in/funding when required, `nop`, exact payment/ASA transfer, then `sendTransfer` with asset ID, quantity, recipient bytes, destination chain and fee. Use canonical full uint64 decimal IDs and actual typed ulong encoding, not upstream JavaScript safe-number helpers.

Attestation uses `attestToken` and source asset metadata/origin checks. Target VAA submission has deterministic storage/guardian account prerequisites, bounded `verifySigs` chunks under the official verification logic signature, `verifyVAA`, then `receiveAttest` or `completeTransfer` with the exact foreign asset/apps/accounts. Recipient asset opt-in requires that recipient's actual signature; the payer cannot impersonate it. Existing authoritative opt-in can satisfy this prerequisite without any new signature. For an external recipient without server custody, expose a wallet-authenticated participant preparation/submit flow: persist the exact unsigned opt-in transaction/group first, bind operation/asset/account/genesis/fee caps and a domain note to the signed message, return it to that recipient's wallet adapter, then verify the complete signed wire against the saved unsigned message and expected public-key/address before submission. No appended group member, rekey, close destination or substituted asset/account is accepted. This participant consent is for that precise opt-in only, not source transfer or another account. Signature response loss reuses the saved transaction identity and authoritative opt-in observation. Solana ATA creation may be payer-signed under the actual ATA program for the exact mint/owner; it never implies ownership of recipient keys, and non-ATA participant mutations use the same exact-message signature workflow. Legitimate program-controlled storage accounts may use only verified official logic-signature templates and their specified rekey-to-application behavior. User-wallet rekeys or arbitrary logic signatures are rejected.

Group construction retains every transaction and signer role; user custody signs only its exact members and provider-owned logic signatures sign only matching official program bytes. Verify fee pooling, minimum-balance funding, all close/rekey fields and group digest. Confirmation recursively identifies the configured core application's publication within the exact inner transaction tree, validates the transfer app call and payload, and decodes uint64 sequence from its authenticated log. Do not copy the SDK helper that takes an arbitrary inner log's first eight bytes.

## Frozen intent, normalization and costs

New `WttIntentV1` freezes actor, acting tenant, original request key/hash, source/target descriptors, source wallet and target recipient identity, original asset origin/address, source representation, source and target decimals, requested amount, actually debited amount, normalized WTT amount, relayer fee and net received amount, dust disposition, native/wrapped output selection, source payer, target payer/recipient participation and per-chain fee/rent caps. Base units and IDs are canonical decimal strings; protocol byte addresses remain fixed-size canonical hex internally. Quote expiry gates new admission, not recovery of already authorized wires.

For decimals above eight, normalize by integer floor and derive the actual transferable base-unit amount; reject zero normalized transfer. Show source dust retained/refunded according to the actual protocol path. For decimals at or below eight preserve protocol units. Derive target amount from the origin/wrapped representation and validate its native range before source effects. Fee cannot exceed amount; normalized fee/net amount and rounding must match the emitted payload exactly. Standard ERC-20/SPL/ASA assets are the baseline; unsupported transfer-tax/rebase/hooks/frozen/authorization mechanics produce an explicit capability refusal before source transfer, not successful underpayment. No implicit infinite allowance.

Quote includes source and target prerequisite fees, message fee, bounded allowance/opt-in/ATA/storage/wrapped-registration costs, guardian posting steps and required participant signatures. Each chain has a distinct fee currency and independent caps; do not sum ETH/ALGO/SOL into an unlabeled scalar. Network fees and permanently retained prerequisite deposits are disclosed separately from transferable amount. Later fee exhaustion requires explicit additional quoted consent; it cannot silently enlarge original caps or release an uncertain original operation.

- `IWttTargetModule`: inspect target registration/accounts and required participants; quote target prerequisites; prepare/submit/observe exact target stage; inspect authoritative body completion.
- `IWttGuardianStateSource`: read guardian index/keys/expiration/current-set evidence from the configured trusted core state at a pinned finalized observation, preserving provider ownership of account codecs.

Generic orchestration is `WttLifecycleService`, `IWttStore`, `WttRecoveryWorker` and one action resolver domain `wtt`. New provider partials are `*.Wtt*.cs`; no editing root's native cleanup or A's DEX paths. Reuse custody, canonical serialization, chain identity, preparation journal and nonce allocation with distinct WTT domain keys; no duplicated generic signers or arbitrary generic-native instruction gateway.

POCOs: WttOperation (immutable intent/quote, participants, stage/generation/version, history, prepared reference, submission authorization, source publication/proof/settlement evidence, next poll time); WttPreparedStage (unique operation/chain/stage/generation, exact unsigned plan and signed wire fill-once); WttProofClaim (unique protocol/environment/core+body digest and unique emitter identity); WttGuardianSnapshot (verified bounded cache with provenance/expiry); WttStageKeyEnvelope (unique operation/role/generation, versioned authenticated ciphertext/public key); WttRecoveryAudit. Raw atomic transactions are reserved for operation+proof claim and final settlement/projection or action authority fences; ordinary access uses typed Surreal builders.

Admission creates exact actor/tenant/key intent before external effects. New source/target signing requires current actor/participant custody and value access. First-send authorization is a versioned CAS, action-bound where applicable. Worker eligibility requires already authorized saved wire; observation may persist the next required stage but never sign it. Quotes are read-only; claim/preparation identity wins before custody. Ethereum nonce allocation and Solana/AVM validity evidence survive retries. New generation requires authoritative no-effect proof, archived costs and explicit applicable consent.

## Guardian transport, proof and replay

Fetch attestation by exact source emitter/sequence from configured HTTPS guardian transports with bounded request/body/time, status-aware pending retry and no caller URLs. Response loss/404 means awaiting proof, never source failure or refund. Persist received envelope before verification and minimize logs. Guardian authentication comes from verified core guardian-set state, not the HTTP endpoint itself. New guardian sets/rotation use actual authorized on-chain state and reject empty, mismatched or expired sets according to protocol rules; no mutable config allowlist bypass or hardcoded quorum shortcut.

Parse each VAA strictly. Signature indices are unique/increasing and in range; cryptographic signatures verify the canonical double-keccak body digest, with quorum derived from the authoritative set. Reparse body emitter, uint64 sequence, nonce, consistency and WTT payload. Match source transaction publication, registered source token-bridge emitter, asset origin, amount/fee, destination and recipient to the operation. On-chain target verification remains mandatory even after local verification.

Ledger uniqueness is domain-separated canonical body digest plus an emitter-chain/emitter-address/sequence conflict index, scoped to Wormhole environment and trusted core identity. Valid alternative guardian subsets for the same body share one claim. Different bodies for one message identity quarantine. Raw envelope bytes remain evidence only; migrate the old full-envelope-SHA256 replay calculation and its tests together. A source transaction can emit multiple messages, so transaction hash alone is not proof identity.

Claim ownership precedes target submit. A claimed proof is not completed consumption. Final target evidence atomically settles proof claim and operation projection; lost projection is repairable without repeating mint/redeem. Concurrent proof submitters and existing on-chain completion are reconciled by exact message identity. No timeout or operator absence assertion can free a possibly submitted claim.

## Public states, APIs and return transfers

States distinguish Admitted, AwaitingSourceAuthorization, SourcePrepared, SourceSubmitted, AwaitingAttestation, AwaitingTargetParticipant, AwaitingTargetAuthorization, TargetPrepared, TargetSubmitted, Settled, FailedNoEffect, CancelledBeforeEffect and NeedsOperator. Successful prerequisite effects remain visible even when a later transfer fails. Fees/rent/approvals are not described as reversed merely because the transfer is not settled. Public receipt contains exact saved operation, stage, required actor role, all transaction identities and confirmed evidence/costs.

Authenticated `/api/bridge/wtt` endpoints: quote, start with Idempotency-Key, participant-scoped cursor list/get, lookup/cancel by original request key with atomic admission tombstone, continue/accept for required authorized participant, read-only refresh, return quote/start, and audited operator inspect/reconcile. SDK mirrors typed intent/quote/receipt/participation and decimal amounts; existing bridge UI and action Bridge/Back route to this domain for WTT, while trusted mode remains explicitly separate. Server discovery survives cleared browser storage. Unknown/awaiting receipt is never an action successor success.

A return is a new linked WTT transfer of the currently held representation back to the origin, with current holder authority, independently bounded quote and exact original settlement link. It reuses the same source/target modules in reverse. A requester cannot grant itself a recipient's signing authority. Outbound VAA still redeemable precludes automatic source compensation. Cancellation before first source transfer may leave confirmed prerequisites; display retained effects and recovery explicitly. After source publication, a UI cancel cannot invalidate the signed message or promise refunded value.
