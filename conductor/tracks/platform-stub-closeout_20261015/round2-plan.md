## Lane A — wallet identity, hosted providers and operator recovery

1. Implement a generic wallet proof dispatcher with real EIP-191 personal-message recovery for Ethereum and Ed25519 verification for Solana, retaining Algorand verification. Use vetted existing libraries and captured normative contracts. Specify accepted signature encoding in SDK/browser contracts and verify the exact server-issued message bytes. Wrong domain, chain, address, malformed encoding and unsupported algorithms fail closed.
2. Apply one chain-aware wallet identity representation at challenge creation, nonce lookup/consume, login, linking, account creation and per-wallet limits. Ethereum uses the existing EIP-55-aware validation with a canonical storage key; Solana remains case-sensitive. Bind challenges to their exact issued identity and ensure equivalent Ethereum spellings cannot create or link multiple accounts. Preserve single-use nonce consumption, atomic wallet-binding uniqueness and no-account-takeover semantics under concurrent requests.
3. Replace touched wallet challenge/claim persistence duplicates and raw basic CRUD with public typed POCO/query/mutation surfaces. Preserve conditional consume and expiry. Unexpected store failures must not become authoritative absence. Follow directory documentation and exception-boundary conventions.
4. Add explicit validated per-network Ethereum chain IDs. A missing/malformed required pin cannot silently adopt the RPC chain. Preserve compatibility only through an explicit validated migration, not fallback to an ambiguous global identity. Update documented configuration, local deployment overlay, tests and SDK network contracts as required. Every signing/activation/recovery path checks its intended network before effects.
5. Implement Veriff's actual hosted API, authenticated callbacks and authoritative result retrieval using the shared durable admission/attempt/lease/outcome machinery. Capture official endpoint/response/recovery contracts before coding; existing raw captures document HMAC rules. Verify subject/session/attempt/provider/tenant linkage and AML evidence; do not interpret an arbitrary approval string as sufficient verified identity. Ambiguous create remains quarantined unless the specific provider proves idempotency or authoritative recovery.
6. Define and implement a versioned AZOA generic-hosted provider protocol with explicit request/result schema, authenticated transport/callbacks, authoritative result fetch, subject evidence, immutable attempt correlation and durable creation/recovery semantics. This is a documented interoperable adapter contract, not arbitrary JSON mapping or a simulator granting approval. Publish executable protocol fixtures and configuration validation. A provider claiming this version must satisfy it.

   Only operator-configured trusted provider origins/issuer keys can implement this protocol for approval. A request may not nominate its own endpoint or signing key as an identity authority. Authentication, redirects, allowed origins and webhook key rotation must preserve that trust boundary.
7. Generalize operator hosted-session recovery through provider capabilities rather than Identomat casts. Add authenticated SDK/frontend journeys for list, evidence inspection, verified attachment, proven-unsent release and sent quarantine. Preserve recent operator authorization, audit reason and exact admission identity. Inspect Stripe inbox replay and add missing usable SDK/UI parity without weakening existing payment/account bindings.

Acceptance evidence authored: real signature vectors, wrong-message/domain/address and canonical-case cases; concurrent nonce/binding tests against Surreal; network mismatch before signing; provider HTTP/authentication/subject/retry tests; authenticated operator recovery and stale/ambiguous evidence UI tests. Actual missing Veriff/generic external deployments cannot excuse missing implementation or protocol tests, and no new live-acceptance blocker is claimed without evidence.

## Lane B — durable action progress, NFT convergence and governance

1. Introduce a durable external-operation pending result for action nodes, preserving the original immutable request/lifecycle identity before any retry can cause an effect. Park expected participant/finality waits without consuming ordinary failure retries. Reconcile the exact saved operation and advance successors only once after terminal proof.
2. Repair missing/Pending/Running replay semantics. A crash after node claim must neither complete an orphaned saga step nor reset an ambiguous economic operation for blind execution. Classify each effectful handler's resumability and integrate its durable operation identity. Existing exactly-once/value guards remain mandatory. Unknown outcomes remain reconcilable, not fabricated success.

   Before changing replay, publish a bounded matrix of every registered handler: pure repeatable computation; transactional/idempotent datastore mutation; durable economic operation with authoritative lookup; or external irreversible delivery. For each effectful row name the stable operation key, admission boundary, authoritative resume method and successor condition. Extend missing local idempotency contracts rather than blanket re-running handlers or disabling them as complete. External response loss without a documented dedupe/lookup guarantee retains an explicit ambiguous outcome and audited reconciliation; absence of such a guarantee cannot be replaced by a timeout or reset. Add representative crash tests for each actual category, with targeted cases for each exceptional handler.

   Implement the authenticated operator reconciliation contract for ambiguous handlers that cannot automatically observe a definitive result; an indefinitely parked record without a usable recovery journey is not closure. Preserve the external effect's evidence and authority, and never let a human absence assertion release a possibly-sent economic effect. The matrix must name Round 3 DEX/bridge dependencies explicitly instead of claiming those routes complete here.
3. Add a dedicated NFT reconciliation service and worker for already admitted egress and confirmed projection. It may observe, replay exact already-authorized bytes and commit final ownership; it must never prepare new signatures, start another generation/stage, accept for a participant, or reinterpret tenant consent. Process fairly across pending records/networks; isolate record/provider outages at the worker boundary and preserve cancellation. Interactive refresh remains the route for fresh participant signing.
4. Integrate mint/transfer/refund/burn/revoke action adapters with pending lifecycle semantics. Reuse Round 1 issuer provenance, fee authorization, source identity and participant acceptance. CredentialRevoke gate removal requires separate review of direct/action authority and durable waiting, with tests authored before the final integrated gate.
5. Fix the actual remaining governance defects: authorized immutable electorate at proposal creation across direct Holon and action APIs; required close policy/time and authenticated close/finalize authority; atomic vote/close boundary and unique eligible voter identity. Reuse the existing claim-ledger tally and vote-of-record guards. Protect membership, in-flight ballots and quorum/finality from forged rows, cross-tenant callers and concurrent closing. Independently review before removing all corresponding publish/dispatch/catalog gates together, and reconcile stale documentation.

   The reviewed conservative policy is a required future `closesAt`, server-enforced voting cutoff and owner-tenant-authorized finalization after that cutoff, with no implicit early-close privilege. Freeze the electorate definition and quorum/finality terms at proposal creation; define and test membership/person identity and revocation handling consistently with existing claim-ledger semantics. At the common direct/action chokepoint, prove authenticated actor ownership or an explicit delegated governance capability over the named tenant. `TenantAuthority.CheckAsync` only proves that a tenant exists and is provisioned; it is not caller authorization. The implementing lane must document its concrete field/role mapping for independent review before gate removal. This is a conservative implementation choice within the user's existing authorization, not a request for another user approval.

   Finalization atomically persists an immutable eligible-vote/tally snapshot and its cutoff/evidence identity. Later claim decision changes, releases, membership edits or repeated tally requests cannot silently alter a finalized result. Any separately supported appeal/replacement is a new explicit audited operation, not mutation of the settled tally. Cover close/finalize/claim-release races in persistence tests.

Acceptance evidence authored: crashes at claim/admission/egress/projection, lost response, concurrent recovery, late participant acceptance beyond retry budget, canceled/failed operations, no successor before confirmation and once-only successor admission; worker no-signature assertions and fairness; cross-tenant electorate rejection, duplicate voter and vote/close races, claim-ledger-only tally and issuer-only revoke.

## Lane C — executable bundle deployment and typed chain capabilities

First deliver a concrete contract amendment for independent review. The existing JSON-only generator and fabricated transaction receipt cannot define a valid deployment. Distinguish two explicit supported targets:

- Platform graph deployment: generate a versioned executable artifact using the existing validated action graph/interpreter and SDK runtime, with authorized bound references, immutable manifest/code digest and an actual invocable runtime registration. Provide the executable loader/artifact and a resolvable deployment identity/invocation route; storing another configuration JSON or setting a status does not qualify. TargetChain is the execution-chain context, not a claim that arbitrary graphs compile to native chain bytecode.
- Native chain deployment: require a concrete typed source/compiled artifact contract and authorized deployment wallet/tenant, then use real prepare/persist/submit/observe to obtain a confirmed contract/application/program identity. Do not invent a compiler for arbitrary config dictionaries. Explicit native-artifact input and real supported compilation/toolchain requirements must be reflected in API, SDK, UI and generated output.

The amendment must settle artifact formats, generation inputs, activation/invocation behavior, ownership/reference checks, supported chains, signer/fee consent, immutable versions, target override behavior, receipt schema and crash recovery before source changes. Existing public generation/deployment consumers must migrate coherently; no unsupported response or renamed JSON counts as completion.

Require an explicit deployment-target discriminant in the public contract and UI. Do not silently reinterpret an existing native-chain request as platform activation. Snapshot immutable graph nodes/configuration/edges, artifact hashes and bound reference/version descriptors at generation/admission. An invocation uses the current authenticated actor, tenant and scoped consent and revalidates current authorization to referenced resources; the deployer's ownership never grants every future caller the deployer's signing authority. Keep credentials and server secrets out of generated artifacts and public metadata. The runnable platform artifact must execute through a concrete registered runtime route and be exercised as such, not merely deserialize another manifest.

Native toolchains accept defined source/bytecode/ELF/TEAL formats and fixed compiler options with recorded compiler identity. Uploaded artifacts are data, never arbitrary host scripts or shell command fragments. Bound source size, compilation resources and deployment steps; validate program/account/instruction identity before custody. Explicitly bind fee/rent budgets, fee payer, recipient of closed-account rent, deploy/update authority and program immutability/upgrade policy to the admitted operation. Multi-transaction upload/finalize paths retain the exact artifact and authority through crash recovery. No deployment may silently select an operator signing key for a user artifact.

After amendment acceptance:

1. Implement real generation/activation and native deployment using shared operation/provider boundaries. Preserve immutable artifact/version/target/request identity before side effects, idempotent response-loss recovery, and explicit Pending/Failed/Confirmed states. Apply validated target overrides before admission; changed artifact/target under one key conflicts. Dapp series, action adapters, SDK and dashboard report deployed only after the corresponding runtime activation or chain confirmation. Coordinate action pending integration with Lane B.
2. Extend chain-call/deployment interfaces with typed Algorand AVM source/program/schema/account/argument inputs and Solana instruction/program-artifact/accounts/authority inputs. Carry signer, fee payer, rent recipient, intended network and stable preparation identity. Reuse chain-owned canonical encoding and durable transport; do not execute arbitrary untyped dictionary content or emit synthetic identifiers. Ethereum retains its shared durable nonce allocator.
3. Complete standalone Solana metadata create/update, ATA creation and token-account closure with explicit custody authority and payer. Reuse NFT metadata/PDA codecs and token instructions, while respecting metadata mutability/update authority and safe account ownership/close-authority/balance/rent destination. Existing immutable NFTs must remain immutable. Match SDK/.NET behavior and document legitimate protocol restrictions separately from implementation gaps.
4. Implement Algorand application deployment/calls and Solana program deployment/calls for the defined artifact contracts. Verify compiler/artifact identity and confirmed application/program result. Deployment sequences that require multiple transactions need durable stage recovery and exact replay, not a single fake terminal receipt.

Acceptance evidence authored: executable generated artifact/invocation; real local program/application deployment and call fixtures; target mismatch and changed artifact/replay rejection; ownership/signature/fee/rent guards; source-to-artifact identity; partial deployment crash recovery; immutable metadata rejection and authorized mutable update; absent ATA creation and safe closure; SDK/UI status correctness.
