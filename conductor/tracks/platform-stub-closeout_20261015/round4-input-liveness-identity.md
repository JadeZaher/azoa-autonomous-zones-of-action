## Flagged but NOT independently confirmed (parallel-agent report, partially corroborated)

A teammate agent (session `a65b9a0e1e5abfb38`) reported that SurrealForge 1.2.0's typed-read path (`SurrealQuery<T>.From().Where(row => row.EnumField == X.Member)`) lower-cases the enum member for the generated SurrealQL comparison, while `SurrealWriter.Create/Set` persists the PascalCase enum name — so a **typed read filter on an enum-typed state column never matches any row**, silently emptying every due-scan built that way. They cited `SurrealConsentWebhookDeliveryStore.cs:23` and `SurrealActionWebhookDeliveryStore.cs:23` as confirmed instances, and said `UpdateOnly`/`DeleteOnly` write-side predicates are safe (re-parsed to PascalCase).

What I independently verified:
- `SurrealConsentWebhookDeliveryStore.cs:23` does read exactly `.Where(row => row.Status == Event.DeliveryStatus.Pending && ...)` via `SurrealQuery<Event>.From()` — matches the flagged pattern exactly. **If the claim is true, `ConsentWebhookDeliveryWorker` never finds a row to deliver**, i.e. every consent webhook is silently permanently `Pending`. No test in the repo would catch this: `ConsentWebhookDeliveryWorkerTests.cs` mocks `IConsentWebhookDeliveryStore` entirely (never exercises the real Surreal store), and no integration test under `tests/**/Integration*` references `ConsentWebhookEvent`/`ListCandidatesAsync`.
- `SurrealForge.Client` 1.2.0 is a NuGet binary-only package in `~/.nuget/packages/surrealforge.client/1.2.0` (DLL + XML docs only, no source) — I could **not** decompile `ExpressionTranslator.NormaliseValue` myself to confirm the lowercasing claim from first principles.
- I checked every enum-typed state query in my domain for the SAME risky pattern. `KycMonitorState.ACTIVE` comparisons in `Services/Kyc/IdentomatScreeningService.cs:355,473` are **safe** — they are plain in-memory LINQ over an already-materialized `List<T>` (`rows.Where(...)`), not a `SurrealQuery<T>.From()` expression tree, so they are not subject to this translator at all.
- `KycSubmission.Status` reads (`GetPendingAsync`, `GetOperatorPageAsync`, the operator-queue read path behind `NodeOperatorController`'s review page) go through a **different** LINQ tier — `Submissions() => new SurrealQueryable<KycSubmission>(new SurrealQueryProvider(_executor))` (`SurrealKycStore.cs:117`), not `SurrealQuery<T>.From()`. Whether `SurrealQueryProvider`'s own expression visitor shares the bug is **UNVERIFIED** — I found no basis in this repo to confirm or deny it, and did not want to extrapolate the other agent's specific citation (which named `SurrealQuery<T>.From()`, not the `IQueryable` tier) onto a different code path without evidence. **This is the single highest-value thing to verify next**: if it shares the bug, the entire manual-KYC operator review queue (`GetPendingAsync`/`GetOperatorPageAsync`) silently returns empty and every manual KYC submission is a CRITICAL permanent dead end with no symptom until someone notices operators never see anything to review.

## Dead-ends, by severity

- **CRITICAL** — `NodeFeeSettlement` recovery/reconciliation workers (`NodeFeeSettlementRecoveryWorker`, `NodeFeeSettlementAtomicGroupReconciler`) exist, are DI-registered, but are called by **nothing** in production code — any interrupted treasury fee settlement has zero recovery path. `Managers/NodeFeeSettlementManager.cs`, `Services/Governance/NodeFeeSettlementRecoveryWorker.cs`, `Services/Governance/NodeFeeSettlementAtomicGroupReconciler.cs`.
- **CRITICAL** — Identomat (the configured default KYC/KYB vendor) hosted sessions that reach `AWAITING_OUTCOME`/`RESUMING` have no worker (excluded from `HostedIdentityRecoveryWorker`), no user-facing refresh (KycController has none), and no operator route (reconciliation query is `State==Claimed` only). `Services/HostedSessions/HostedIdentityRecovery.cs:16-21`, `Controllers/HostedSessionReconciliationController.cs:69-71`, `Controllers/KycController.cs`.
- **CRITICAL-if-confirmed, UNVERIFIED** — possible SurrealForge enum-case translation bug could make `SurrealKycStore.GetPendingAsync`/`GetOperatorPageAsync` (the manual-KYC operator review queue) and `SurrealConsentWebhookDeliveryStore.ListCandidatesAsync` (consent webhook delivery) silently return zero rows forever. Needs a live-DB probe to confirm/deny; not provable statically without SurrealForge source.
- **HIGH** — `KycScreeningMonitorPollWorker` (ongoing AML re-screening) is registered but disabled by default (`MonitorPollEnabled=false`, `appsettings.json:191`) — any node operator who hasn't explicitly flipped this flag has no ongoing sanctions re-check at all, silently.
- **MEDIUM** — `WalletAuthIdentityMigration.Status="Conflict"` has a correct, scoped operator API exit (`WalletIdentityOperatorController`) but **no frontend UI** — grepped and found none.
- **LOW** — `ConsentWebhookEvent` `DeadLettered`/stuck-`Pending` rows are explicitly observe-only by design (doesn't gate signing), so at worst a tenant misses a notification.
