## Prioritized concrete findings

### P1 — Action-graph deployment still reports a fabricated chain effect

`Controllers/ActionGraphBundleController.cs` exposes authenticated `POST {id}/generate` and `POST {id}/deploy`, delegating to `ActionGraphBundleManager`. In `Managers/ActionGraphBundleManager.cs:118-175`, generation serializes Name/Description/TargetChain/BoundHolons/UserConfig into JSON. Deployment checks that this string exists, writes a timestamp and `TxHash = $"0x{Guid.NewGuid():N}"`, then returns the successful datastore upsert. There is no compiler, artifact deployment, provider call, signing authority, or confirmation.

The SDK exposes `generateActionGraphBundleDapp` and `deployActionGraphBundle` in `sdk/azoa-wallet/src/api/client.ts`. The dashboard `action-graph-bundle/page.tsx` labels the generator “Generate dApp” and its JSON output “Generated Code”; its target selection advertises Algorand and Solana. The same dashboard also directly POSTs the deploy route at lines 411-418 and presents a Deploy button/result; the false success is user reachable. The API request contains only target chain, bound Holon IDs and a string config dictionary; it does not define a compiled contract artifact, hosting target, deployment wallet or signed authorization.

The composition pipeline is not an alternative real deployer: `DappCompositionController` exposes `POST /api/dapp-series/{id}/deploy`; `DappCompositionManager.DeployAsync:340` delegates to the same bundle manager and then sets series status Deployed. It accepts `targetOverride` but explicitly does not forward it. `ActionGraphBundleDeployNodeHandler` likewise calls the same manager and reports ActionNodeResults.Ok on its datastore success, advancing a workflow after no deployment. These routes must share the corrected durable result, retain tenant/signing context and original idempotency, and avoid publishing deployed status from mere admission. Existing manifest composition, DAG validation and action/bound-Holon extraction are useful real reuse surfaces; they do not compile or host artifacts.

The plan must resolve that actual contract explicitly. A deployable frontend bundle needs generated executable artifacts, authorized asset/action bindings, content/version identity, a real hosting destination and observable deployment receipt. A chain application deployment needs chain-specific source/bytecode/ABI, actor wallet/tenant signing authority, durable preparation/submission and confirmed application/contract identity. JSON alone is neither. Reusable seams exist in `BlockchainOperationManager.ExecuteDeployContractAsync` and provider `DeployContractAsync`, but the manager currently forwards untyped args and wallet address without a signing-context parameter; Algorand/Solana implementations refuse unconditionally. Ethereum has a real durable preparation allocator, but it must be called through a reviewed authority contract. Do not manufacture a compiler from arbitrary JSON or claim a new unsupported response closes this gap.

### P1 — Action pending semantics can lose workflow progress after a real effect

`Services/Actions/Workflow/ActionNodeStepHandler.cs:588` returns `StepResult.Ok` for a missing/Pending/Running node when replaying advancement. The independent `action-lifecycle-review.md` traces SagaProcessor's successful-step completion, establishing a concrete crash-after-claim orphan path. Expected NFT waits are also still returned as ordinary handler failures rather than durable external-operation waits. Opt-in, recipient authorization and finality can outlast the ordinary failure retry budget.

The new NFT store's background `ListPendingAsync` has no worker consumer. Participant discovery and explicit refresh are useful, but closing a browser after egress can leave confirmed chain effects without final authority/ownership projection. A worker must observe or rebroadcast only already admitted exact wire and perform terminal projection; blindly calling user Refresh can prepare new signatures or cross into a new stage and is unsafe.

Acceptance: persist the original domain lifecycle/request identity with the action execution; park and resume with CAS; no successor before exact terminal proof; no ambiguous effect rerun; concurrent reconciler delivery cannot advance twice. Exercise crash before/after node claim, admission, signed-byte persistence, egress and projection; cancellation/failure; user acceptance after retry-budget expiry; missing/Running replay. Worker acceptance must prove it never impersonates recipient, creator, issuer or tenant signing consent.

### P1 — Wallet authentication and Ethereum network identity are incomplete

`Services/Signing/Ed25519SignatureVerifier.cs:45-53` dispatches only Algorand and throws for Ethereum/Solana. `WalletAuthManager` trims addresses at challenge creation and consumption without chain canonicalization; `SurrealUserStore.GetByAuthWalletAsync:240-263` queries exact address strings. `User.cs` has a unique `(auth_wallet_address, auth_wallet_chain_type)` index, but case variants are distinct strings. Ethereum equivalent spellings can evade intended single-wallet identity unless normalized consistently before challenge, lookup, creation, linking and rate-limit identity. Solana case must remain significant. The challenge store also needs its already-defined public typed model instead of duplicate/raw/catch-all persistence.

Implement provider-owned EIP-191 personal-sign verification and Solana Ed25519 verification over the exact server-issued bytes, behind a generic dispatcher; align browser/SDK signature encoding. Test real signatures, wrong message/domain/chain/address, malformed encodings, canonical linking/login, concurrent nonce consume and concurrent equivalent-wallet binding. Preserve the existing single-use and no-account-takeover rules.

`EthereumProvider.ConfiguredChainId():282-292` reads a single chain-level metadata `ChainId` for all networks and treats missing or malformed values as no pin. `GetChainIdAsync` then adopts the endpoint's response. Enabling Devnet/Testnet/Mainnet cannot give each intended network its own independent pin through this surface. Durable `eip155:` identity protects later replay but does not prove the operator intended the initial endpoint's chain. Add explicit per-network validated identity configuration, no malformed-to-unpinned downgrade, cache/network isolation and mismatch-before-signing tests. This is an implementation/configuration design issue, not an external provider blocker.

### P1 — DEX execution parity remains absent and one success payload is misleading

`TinymanDexAdapter.BuildSwapTransactionAsync:161-180` ignores the cached quote payload, sets TokenIn to QuoteId and TokenOut to WalletAddress, and returns success with prose instructing the client to build a group. `SwapManager.GetSwapTransactionAsync:87-113` advertises an unsigned-transaction build and returns that response directly. The adapter does not produce an executable transaction group or enforce its cached amounts/slippage in one. `Program.cs:1348-1355` registers Jupiter and Tinyman only; Ethereum has no DEX adapter.

Implement actual quote-bound unsigned transactions or the explicitly authorized durable custody path, including network, asset/amount, min-out, expiry, recipient, signer and fee constraints. For client signing, output exact canonical payloads and validate the returned signed payload before any server egress. For custody, reuse prepare/persist/submit/observe boundaries. Preserve no-pool/upstream-unreachable as honest `Unavailable` environment conditions. A missing real pool can block a live exercise, not protocol encoding, fixtures or integration implementation. Jupiter builds an actual upstream transaction; its current opaque returned-wire trust boundary still merits adversarial validation against the cached quote before platform-controlled signing.

### P1 — Wormhole observation and real target settlement are still blocked

`CrossChainBridgeService.cs:166-169` unconditionally rejects the Wormhole mode even with real-value enabled. `Services/Bridge/WormholeProtocol.ObserveAsync` unconditionally refuses authoritative emitter/sequence derivation. Ethereum and Solana implement neither bridge source nor target capability; Algorand implements source only, while the simulated provider implements both. Existing guardian verification is not the missing source-message or real target-redemption implementation.

Required package: provider-owned finalized source-message evidence (chain/genesis, emitter, sequence, source transaction and exact transfer payload), authenticated guardian-set/quorum verification, immutable source/proof/recipient/amount linkage, durable target submission and chain-native replay protection plus local CAS. Reconcile lost source/target responses without minting twice or refunding after target value exists. A source receipt or VAA for another asset/recipient/amount cannot settle this operation. Do not remove the existing kill switch or weaken exactly-once assertions before actual target modules and adversarial evidence tests pass. Deployment addresses/guardian availability may later be concrete external setup, but none excuses the absent code now.

### P2 — Standalone chain contract/account/metadata APIs remain stubs

`AlgorandProvider.cs:741-756` refuses both AVM deployment and calls. `SolanaProvider.cs:570-585` refuses program deployment and calls. Standalone Solana metadata create/update at `629-647` remain refusals despite the new NFT-specific Metaplex helper. `CreateTokenAccountAsync:655-678` only succeeds when the ATA already exists; absent ATA creation fails because the seam lacks payer/signing context. `CloseTokenAccountAsync:681-689` is unconditional refusal.

These are reusable protocol capabilities, not external account shortages. Design explicit authorized operation contracts carrying the required signer/payer/rent recipient, program/application identity, typed instruction/ABI/account inputs, network and immutable preparation key. Reuse the durable signer and provider-owned instruction modules; do not add ad-hoc server branches or fake IDs. Account close must prove ownership/close authority and safe balance/recipient; metadata update must prove update authority and mutability. Deployment must verify real compiled artifact identity and actual application/program result. Define supported artifact contracts concretely instead of guessing arbitrary method arguments.

### P2 — Governance and credential action gates still block advertised nodes

`NotEnabledActionNodeTypes` still blocks proposal creation, vote, tally and CredentialRevoke. Governance's underlying flaw remains visible: `ConsumerGovernanceHolonTypes.ProposalElectorateRejection:142-158` validates declared tenant shape, not the acting caller's authority over that electorate; `HolonManager` calls it without acting-tenant authority. Proposal creation still permits missing closesAt (`GovernanceProposalCreateNodeHandler:124`). A ledger-backed tally alone does not establish a legitimate franchise or final close authority.

Implement immutable authorized electorate binding, explicit open/close/finalization semantics, membership/person uniqueness and race-safe ballot/close/tally behavior across direct Holon and action routes. Then independent review can remove gates and stale explanations. CredentialRevoke's old “issuer equals holder” explanation is obsolete after Round 1 provenance work, but its action gate should be removed only with the pending-action integration and independent issuance/revocation evidence, not by deleting the set entry alone.

## Proposed bounded waves and acceptance order

1. **Round 2A, identity/config lane:** wallet-auth provider dispatch, canonical wallet identity, typed nonce/binding persistence, and per-network Ethereum identity pins. Include SDK/browser encoding and config migration. No production key material in evidence.
2. **Round 2B, durable action lane:** action parked external-operation state, Running crash recovery, NFT authorized-egress/projection worker, action revoke integration. Preserve immutable request keys and no automatic participant signatures.
3. **Round 2C, deployment contract lane:** settle and implement action-graph artifact generation/deployment semantics, remove fabricated TxHash through a real durable deployment path, explicit signer/hosting authority, and typed observable result. Design-review this contract before implementation; relate it to the chain-call wave instead of creating another parallel submission mechanism.
4. **Round 3 parallel protocol lanes:** DEX/Tinyman/Ethereum; AVM/Solana contract and standalone metadata/account capabilities; Wormhole authoritative observation/target settlement. Keep provider ownership, common durable transport and SDK parity. Each protocol lane needs captured official contracts and independent adversarial review before activation.
5. **Governance plus additional identity lane:** electorate/close authority and Veriff/generic hosted protocol. Schedule independently when shared stores/actions stabilize; no permanent disabled-as-complete answer.
6. **Round 4 reassessment and evidence:** fresh dual full-goal scan, final fixes/pruning, generated schemas/flowcharts, integrated build/test/lint/typecheck and local protocol fixtures, Stripe DEV acceptance, independent verifier, required remediation batch, main push and verified branch cleanup. Remaining external facts alone go to deferred.md with evidence and exact unblock steps.

These packages are proposed for plan review, not a grant to bypass the user's four-round process or start unreviewed implementation. Broad scans surfaced candidates; the concrete findings above were checked against actual source paths. Exhaustive behavioral proof of the entire platform remains impossible without the reserved runtime sweep, and that limitation must remain visible rather than replaced with optimism about authored test counts.
