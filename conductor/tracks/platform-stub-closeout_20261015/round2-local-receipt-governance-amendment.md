## Local mutation authority and receipts

The execution envelope alone cannot make an arbitrary manager call replay-safe. Introduce a persisted local command with deterministic identity derived from tenant/actor/run/node and the canonical frozen input hash. It records a prepared mutation plan, expected source record versions/digests, deterministic result identifiers, and a terminal serialized handler result. Preparation has no user-visible effect. Commit executes typed generated mutations and a typed receipt write in one Surreal transaction with a raw atomic precondition boundary. Shared generated-statement parameter scoping prevents multi-writer collisions. A duplicate command returns the exact receipt; changed input conflicts. No state-observation heuristic substitutes for a receipt.

Manager authorization/validation remains authoritative: factor the existing validated local mutation planning out of the affected managers rather than bypassing it with an action-only direct datastore implementation. The plan is bounded and revalidates current actor ownership, tenant consent when applicable, governance policy and all read versions at commit. Persisted actor identity is a scope input, not an authenticated principal. A revoked capability refuses an uncommitted command; a committed receipt remains recoverable. External chain/network effects never enter this local transaction mechanism.

| Handler family | Concrete mutation plan and durable result |
| --- | --- |
| HolonCreate | Deterministic holon ID from command + stage `create`; validated full holon and optional graph edges, atomic receipt. |
| HolonClone | Freeze authorized source subtree snapshot and bounded traversal; clone IDs derive command + original ID, including parent remapping. Commit all clones/edges + receipt atomically, requiring source versions remain unchanged. Reject excessive tree size before effect with actionable bounded-limit error. |
| HolonUpdate/Interact | Prepared exact resulting metadata/fields plus expected target digest/version; atomic target mutation and receipt. Additive interactions execute once, even if the engine dies before observing the receipt. |
| HolonMoveSubtree/Propagate/Delete | Freeze bounded affected-record and parent/edge snapshot; recheck ownership/cycle and versions in commit. Apply all changes and receipt in one transaction; no partially moved/deleted tree. |
| WalletCreate | Persist generated encrypted custody material and deterministic wallet ID as an internal prepared command before public wallet insertion. Reentry uses the saved material; never regenerate after admission. Atomic wallet insertion + receipt; no secret in execution output or operator API. Imported-address wallet creation pins caller input similarly. |
| WalletUpdate/Delete/SetDefault | Preserve current wallet authorization. Atomic exact target mutation plus receipt; default change includes the actor's prior defaults in the same transaction. No local custody deletion is considered a chain movement. |
| LoanOpen | Deterministic loan and initial ledger entry IDs; create both and receipt atomically. No lone tracker constitutes success. |
| LoanRepaymentRecord | Unique source run/node and expected loan version; atomic ledger insertion, resulting status/projection and receipt. Replace process-local lock as correctness boundary. |
| Emit | Deterministic tenant/run/node event ID; atomic unique outbox enqueue and local receipt. Output promises durable enqueue only. Delivery carries same event ID and remains at-least-once at remote receiver. |
| Grant/Fungible post-effect association | Recover authoritative existing domain receipt first; prepare association mutation tied to the exact confirmed asset and actor. Record completion only after association receipt. Never rerun the economic effect to repair a local link. |

This is staged manager/store work within Round2, not a size-based deferral. Legacy Running mutations lacking a prepared command or receipt cannot be guessed/reissued: operator inspection reports the evidence gap, while attach requires domain/receipt verification. New commands must never enter that ambiguous shape.

## Governance authority and field mapping

The tenant in this platform is a user principal; `OwnerTenantId` is child provisioning lineage and consent grants authorize the opposite direction (tenant acting for grantor), so neither is an administrator role. Creation/finalization authority will initially be the authenticated tenant principal itself: actor ID must equal the declared electorate tenant ID, and that principal must be active and pass existing `TenantAuthority.CheckAsync` server provisioning/API-key validation. Equality alone is insufficient. A child token's `ActingTenantId` alone cannot authorize election administration. A separate delegated election administrator is not inferred from existing consent scopes.

Proposal authoritative record uses deterministic proposal ID, tenant ID, creator ID, opensAt, **required** closesAt, ordered declared options, canonical uniqueness scope/key, minimumVotes (nonnegative explicit quorum), electorate snapshot ID/hash, definition hash, CreatedAt, and version. The current Holon remains the public projection, not the authority record. Create/Update/Interact/Delete through raw Holon API enforce that proposal authority is service-owned and immutable; client-authored metadata cannot create or revise an election. A manager-only command prepares the authority + Holon projection in the same receipt transaction.

Electorate snapshot uses membership-rule version 1: tenant itself plus current child users owned by it and participating grantors with a live `Origin=Participation` grant carrying a participation reference to that tenant. Arbitrary UserExplicit wallet/read/payment grants are not membership. Every member must pass existing person-uniqueness/KYC requirements at ballot time; snapshot membership alone does not override verification revocation. Snapshot IDs and membership are internal and never placed on public ballot Holons. Creation stores the exact eligible IDs and a private digest; API publishes only electorate count and terms. Newly added members cannot join an existing election; offboarding/consent withdrawal denies a new vote but does not erase a vote already cast legitimately. The vote service checks current membership and immutable snapshot membership, preventing a tenant claim from enrolling an unrelated user. Persist the cast-time voter identity/eligibility evidence and canonical decision hash; finalization counts that persisted evidence, never current AML/membership.

Cutoff is database-time checked inside the existing person-claim mutation, not merely handler time. Claim decision pins proposal ID, definition hash, option, canonical decision hash and immutable cutoff. Existing same-person uniqueness remains the sole votes-of-record ledger. A governance claim cannot be released or rewritten at/after cutoff, including generic claim APIs, and cannot change its proposal/cutoff definition after first claim. Ordinary non-governance uniqueness claims preserve existing compensation behavior. Final snapshot persists explicit tally-schema version as part of the immutable result.

Finalization requires the current tenant principal, server time >= closesAt, and the original immutable definition. One atomic transaction locks/fences proposal finalization, reads eligible unreleased claim-ledger decisions bound to that definition/cutoff, writes immutable final counts/total/quorum result/tally hash/finalizedAt, and closes the Holon projection. Counting reuses the existing GovernanceClaimLedgerTally counting rules and canonical GovernanceTallyHash representation; it never counts public child Holons. No early-close endpoint or status metadata edit changes the deadline. Concurrent finalizers return the same saved result. Later membership, claim-release attempts or cosmetic Holon edits cannot alter a finalized snapshot.

## Required review and acceptance

Independent approval of this concrete authority/membership mapping precedes gate lifting. Fixtures cover unrelated actor naming a tenant, child-token admin escalation, membership revoked before voting, new member after snapshot, proposal edits from every Holon mutation route, cutoff races, release after cutoff, forged receipt Holons, concurrent finalizers, immutable replay, and local mutation crash before/after commit. Storage fixtures execute real transactions only in the final integrated sweep; source authoring does not claim database semantics were run.
