# Workflow designer

The authenticated DappDevelop controller verifies active tenant ownership and a live, unexpired `tenant:provision` credential before disclosure and every interview. The explicitly selected tenant must match the authenticated owner. Child/acting-tenant credentials are refused. Drafting adds no KYB or value-execution prerequisite. The ordinary authoring API retains persistence and lifecycle authorization; this service has no stores, managers, tools or execution dependency.

## Closed model contract and server-owned language

UI study 03 exposed obsolete tax thresholds/rates, internal field names and a narrative describing a nonexistent draft. Prompt disclaimers and official reading links did not prevent those claims. The provider now selects only five required arrays of closed enum IDs: questions, risks, operational gaps, unsupported capabilities and planning stages. No model-authored prose, resource identifiers, names, configurations, citations or draft is admitted. The native schema forbids additional properties; independent local deserialization disallows unmapped properties, requires every array, refuses numeric enum values, and bounds depth. The service rejects null, oversized and undefined selections before producing public state. Malformed replies are typed refusals, never an empty ready proposal. No fence stripping, healing or retry is used.

`WorkflowDesignerCatalog` owns all visible wording and graph names/configurations. Questions cover operating facts and jurisdiction-specific adviser review, including the relevant tax year, payer/payee classification, payment/source/residence facts and local professional determination. Canonical concerns supply no statutory rate, threshold, form-filing conclusion or compliance approval. IRS/FinCEN/SEC links are US reading starting points, not citations proving a workflow-specific conclusion. This design constrains the output channel; it does not establish complete legal coverage or prove that selected questions are relevant or sufficient.

Operational gaps block a proposal. Professional review remains necessary before real operation but is a separate nonblocking checklist for planning. Duplicate IDs and generic questions in an already specifically questioned dimension are removed; distinct specific questions remain. Only whole-answer uncertainty sentinels mark an otherwise substantive intake field unanswered. Context such as an unknown payment state frozen for investigation and user amounts/allocations remains valid input. The model still judges semantic completeness and may select an unnecessary follow-up; the service does not claim semantic proof.

## Explicit planning scope and truthful state

The default scope is interview only. A draft additionally requires explicit planning/data-only opt-in, six substantive operating dimensions, user fact confirmations, no remaining operational questions and a meaningful selected handoff outline. User confirmations establish stated facts, not professional approval. The server materializes a canonical private linear graph with Emit nodes that record fixed planning/manual-external-handoff data. Nodes contain only the server-owned checkpoint enum and scope/fundsMoved/requiresExternalReview flags; user prose and arbitrary identifiers never become graph configuration. Request and records notes bracket the distinct selected stages.

This is an importable starting point for visual authoring. It does not implement or enforce two-person approval, eligibility, caps, deadlines, refunds, payouts, idempotency or settlement. A checkpoint neither waits for nor proves external review/payment. Exact user amounts and business rules remain in the brief for separate implementation; the graph does not embed or enforce them. Users can continue interviewing or use the full manual builder for an executable workflow. UI scope, review and import labels state these limits plainly.

Import itself does not execute the graph. Emit is a real notification primitive: a later explicit run requires an active tenant registration and can enqueue webhook notifications to its configured destination through the durable outbox. This is not a notification-free or inert graph when run. Scope, description, limitations and review acknowledgment disclose this side effect and prerequisite. No QA execution of the graph is authorized by this source correction.

The existing strict config, DAG and binding-executability validators independently validate the materialized graph. The general policy's resource provenance/hold-reference defenses remain tested for any future supported expansion. `DraftReady` and `readyForDraft=true` occur only with an actual validated non-null graph. Failed validation clears the graph before canonical state wording is chosen. Import does not save, publish, run or move funds.

## Provider privacy and budget

OpenRouter transport is pinned to the HTTPS completion endpoint, uses a server-only bearer, disables redirects and fallback, requires schema support and deny-data-collection routing, bounds response bytes and uses a 90-second deadline. Cancellation propagates. Neither bodies nor credentials are logged. The provider receives intake, fact/scope choices and bounded user/assistant history after explicit disclosure acceptance; it receives no tenant ID or confirmed resource handles. Submitted history cannot add system/tool roles. The interview is stateless on the API and memory-only in the browser; account change discards it.

`WorkflowDesigner__Enabled`, `WorkflowDesigner__ApiKey` and `WorkflowDesigner__Model` are server configuration. Never copy a key to frontend variables, source, arguments or traces. The canonical tenant-owner partition shares its hourly budget across that owner's keys/JWT sessions. RequestsPerHour defaults to 12 and is clamped to 1-60. This per-instance limit and the 4,000 output-token cap do not constitute a fleet monetary limit; providers may also charge input/reasoning. Provider-account limits remain an operational prerequisite.

Native strict-schema routing was checked against official OpenRouter documentation and Sonnet 4.6 endpoint metadata on 2026-10-18: https://openrouter.ai/docs/guides/features/structured-outputs and https://openrouter.ai/api/v1/models/anthropic/claude-sonnet-4.6/endpoints. The closed catalog narrows that reviewed transport contract without adding provider calls. Current batch execution and live UI proof remain coordinator-owned.
