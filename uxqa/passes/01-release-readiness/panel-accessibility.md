# Scope and decision

Pass 01 contains confirmed accessible-name and automated contrast findings. It also contains a keyboard-access warning for an Overview scroll region. These observations justify remediation and targeted browser verification, but they do not establish a human exclusion rate or full WCAG conformance. The completed desktop keyboard journey and pointer-driven zoom journey do not clear the unnamed collapsed navigation control for screen-reader users.

This lens read the plugin's `reference/research-panel.md`, this pass's scenario, personas, four lane reports, `ux-report.json`, and the `axe`, `attempts`, `outcome` and `note` fields from every run's `ux.json`. It visually inspected `runs/qa-uxqa-zoom--zoom-slow-account/overview.png`. It did not read application source, session/account files, provider responses or `trace.zip`, and did not run a browser or change the application. All paths below are relative to this pass directory.

Findings describe the image exercised in pass 01. Refreshed images, subsequent fixes and the tenant AI designer were not exercised by this lens. None is marked resolved on the basis of source review.

# Human validation and refreshed-image verification

Run **five human sessions per affected segment**. Sessions may cover several findings, but keep segment results separate; this agent study supplies neither recruitment nor a human success rate.

| Segment, five sessions each | Tasks and measurements | Evidence that would kill or narrow the impact hypothesis |
| --- | --- | --- |
| Screen-reader users using the collapsed navigation | Starting on Overview at the constrained viewport, find Settings and identity status using the participant's usual assistive technology. Record announced menu name, discovery, unsuccessful activations, independent completion and recovery. Repeat on Wallets. | All participants independently identify and operate navigation without guessing or coaching would weaken the exclusion hypothesis. It would not make a verified absent programmatic name compliant; name exposure still needs an objective check. |
| Keyboard-only developers | Reach Wallets, Settings and identity; then scroll Overview through all status content without a pointer. Record initial focus, navigation keys, ability to reach the scroll region, content reached, focus visibility and a second repeated attempt. Ask about any discovered bypass mechanism. | Independent access to all content with ordinary keys kills the claim of scroll-based exclusion. Efficient repeated access through an available bypass mechanism narrows the 52-key effort hypothesis. A forced pointer workaround raises severity. |
| Low-vision developers using magnification | At real 200% browser zoom and their usual settings, read account/identity status, distinguish disabled controls, open navigation and describe the chain-unavailable messages. Record misread text, horizontal/vertical navigation, task effort and any missing content. | Accurate unaided reading and full content access weaken predicted task harm. Measure contrast separately: successful reading by five people does not invalidate a failing WCAG ratio. Actual reflow failure would create a new finding rather than retroactively change pass01. |
| Low-vision interrupted operators | Read readiness, find audit, explain provider status/freshness, then return to the interrupted task. Include the recovery screen in the reading assessment; do not perform administrative writes. | Correct independent interpretation without rereading or coaching narrows the predicted status-reading impact. Wrong interpretation linked to low contrast or off-screen controls supplies stronger consequence evidence. |

Before release, a refreshed-image pass should capture the actual accessible name, rerun axe on the same routes/layouts, and directly exercise keyboard scrolling and dialog focus. Store new artifacts under a new pass/task identity and retain the old evidence. Confirmation must use the running image; a source-level change or unit test alone cannot close this lens's observed finding. Tenant AI interviewing, warning text, consent and graph import need their own constrained task scenarios; pass01 cannot stand in for those tests.

# Limits and contradictory evidence

The desktop keyboard path completed without a focus trap, the pointer-driven zoom path completed without a workaround, and corrected mobile navigation completed. These are useful positive observations. They coexist with the missing-name/contrast evidence because they exercised different capabilities. Neither no recorded failures nor one agent's inference establishes universal accessibility.

The initial mobile ABANDONED run was a strict-locator ambiguity before any click, not evidence of human abandonment or a navigation barrier. The member-settings gold task is PARTIAL while its recorded attempt is successful; the coordinator identified a client-navigation/predicate timing issue. Treat it as unresolved harness evidence until corrected, not as proof that keyboard or menu access failed. The capability probe is excluded from UI conclusions. The operator's initial no-TTY run did not exercise the UI; its disclosed overwrite limits run-history integrity without invalidating the later recorded route observations.

There are 11/57 visited routes (19.3%), below the 20% target. Axe counts are rule-route scan occurrences, not unique defects or affected humans. The report's comparison to `00-setup` is not a meaningful usability trend: setup smoke and pass01 have different tasks. No two-pass success trend exists. Agents are patient, literate and undisrupted; the desktop agent can navigate dozens of controls without the fatigue, missed labels or confidence loss a human may experience. Conversely, strict automation selectors can create failures humans would never encounter. No application-wide WCAG conformance, release approval or completed human validation is claimed.
