# Content designer lens

The observed language generally let the agent personas distinguish ordinary account access from operator access, understand empty wallets and an unstarted identity check, and inspect operator configuration without changing it. The strongest content concern is the overview's duplicated technical failure message: it reports a JavaScript exception without explaining the affected service or the next useful action. Provider freshness and recovery ownership also need human comprehension checks. These are hypotheses about user impact, not human research findings or confirmation that later fixes work.

Evidence reviewed: [scenario](scenario.md), [personas](personas.json), [aggregate report](ux-report.json), the four lane reports, and each of the nine run records' steps, attempts and outcomes. The provider and mobile operator-login screenshots were inspected. No application source, other lens reports, private trace, session file, browser or API was consulted. Scores use impact × frequency × segment breadth, each 1–3; breadth describes supported affected segments, not all possible users. Proposed language below is a direction for validation, not a claim about implemented behavior.

For CD-01, test a short status naming the affected chain and unavailable information, with a next action only if the UI actually supports it. Avoid promises that balances or transfers remain operational without evidence. For CD-04, test explicit “Not configured” or “No saved policy yet” only after triage establishes the actual state. Preserve the operator page's useful distinction between configuration flags and secret values: the screenshot says values are write-only host secrets and are never returned to the console. Its Development-only manual-review warning also explains a concrete production restriction.

## Useful language and unresolved questions

The empty-wallet labels “No wallets yet” and “No balances” supported the observed read-only tasks. Identity copy explained that verification had not started and connected it to adding funds and cashing out. The disabled Refresh result control had no separately observed explanation; context may be sufficient, but this needs a comprehension question rather than an automatic defect. Five returning developers should explain when refresh becomes useful before attempting verification. No participant should submit identity documents in the research exercise.

The landing page introduces financial workflows, circular economies, operational processes, grant programs, actions, holons, rails and bundles. The mobile persona read it and found sign-in in the corrected run, but that establishes reading and navigation rather than comprehension. With five low-literacy mobile newcomers, ask for a plain-language description of what they can create, then ask them to sign in. Kill the jargon/discovery hypothesis if all five can explain the offer and find sign-in unaided without a costly detour. Do not rewrite specialist vocabulary solely because this reviewer finds it unfamiliar.

## Automation and metric interpretation

- The initial mobile ABANDONED record contains two strict-locator failures before any click because LOGIN matched two elements. This is automation ambiguity, not evidence that a person could not understand LOGIN. The corrected run completed in 30 seconds with two clicks, no failed attempts and no workaround. Keep both artifacts.
- The member Settings gold task is PARTIAL even though its single recorded attempt succeeded. Its record alone does not show a user failure; coordinator evidence identifies an immediate destination predicate before navigation settled. Reassess after a correctly synchronized gold run. The separate keyboard and zoom journeys reached Settings.
- Anonymous operator redirects and an expected 401 during session recovery are not copy failures by themselves. The successful recovery gold task establishes reaching the sign-in explanation, not recovering lost credentials.
- The aggregate contains eight UX records and one excluded capability probe. It visits 11/57 page routes (19.3%), below the declared 20% target. Setup pass 00 is not a comparable research baseline. Do not infer a friction regression, a two-pass trend, or a human success rate from these totals.
- Colour-contrast detections may make otherwise useful text unreadable, including operator sign-in form labels. This lens did not measure contrast independently; retain automated evidence for accessibility triage rather than asserting every detected node is a separate copy defect.

## Human validation plan

Run **five sessions per affected segment** with disposable, consented accounts and no value movement or administrative writes. These are proposed sessions; none has occurred.

| Segment / sessions | What each session must test | Evidence that would kill or reduce the hypothesis |
| --- | --- | --- |
| Five returning members using 200% zoom and slow connections | Explain duplicated chain status, identify what is unavailable, select a safe next step; locate account-only settings; explain disabled identity refresh. Tests CD-01 and CD-03. | Participants correctly bound the outage, continue appropriately, identify scope without coaching and explain refresh from existing text. No costly detour or unsafe intention. |
| Five keyboard/screen-reader developers | Find and name the navigation control through their normal accessibility tools; reach Settings and describe account versus tenant controls. Tests CD-02 and CD-03. | The control is discoverable and operable by an appropriate name, and all participants explain scope correctly. Pointer success cannot kill the naming hypothesis. |
| Five interrupted operators, including operators who do not manage deployment secrets | Explain the provider timestamp and readiness, identify the person responsible for credential recovery, and distinguish ending this browser session from global revocation without activating either. Tests CD-04 and CD-05. | Operators interpret freshness accurately and state an actionable, correct recovery handoff without assuming this form can reset credentials. |
| Five low-literacy mobile newcomers | Explain the offer in their own words, find ordinary sign-in, distinguish it from operator sign-in, and explain what to do when account recovery is unavailable. Tests landing-language question and CD-05. | All five identify the appropriate entry point and a correct recovery owner unaided, with a coherent plain-language explanation of the offer. |

Agents are unusually patient, literate and task-directed; no participant distractions, real financial uncertainty or actual credential loss were reproduced. Read-only empty-state journeys do not establish the comprehension of consequential writes. No legal/tax guidance, tenant AI interview, draft workflow, save/publish behavior or LLM interaction was exercised in this pass. Add that surface to a later scenario and evaluate it independently. Source changes or reported fixes cannot validate any hypothesis here; rerun observed routes and human comprehension checks against the built candidate.
